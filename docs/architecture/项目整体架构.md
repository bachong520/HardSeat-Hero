# 项目整体架构

## 1. 项目定位

HardSeat Hero 是一个前后端分离的低价火车路线查询本地 MVP。用户输入出发站、到达站和出行日期后，系统返回直达或中转方案，并以最低总票价作为主排序目标。

项目已经从纯 Mock 原型演进为包含真实数据源适配、SQLite 静态票价库、OD 缓存、搜索遥测、刷新脚本和诊断脚本的本地系统。当前架构重点是：

1. 降低远程 12306 公布票价接口 I/O。
2. 通过静态票价库提升常见 OD 命中率。
3. 用搜索遥测反哺刷新 OD 队列。
4. 保持搜索正确性，不把历史最低价当作安全 lower bound。
5. 通过 `ROUTE_SEARCH_ENGINE` 在旧候选中转站 OD 搜索和本地时间扩展图搜索之间切换。

明确不做：

- 用户登录、收藏、支付、购票、抢票。
- 全国 OD 暴力采集。
- 把静态公布票价等同于实时余票。
- 把长周期刷新任务放入 FastAPI 请求链路。
- 把历史最低价作为 A* 硬剪枝 lower bound。
- 把本地静态公布票价等同于实时有票或全国完整覆盖。

## 5. 前端请求链路

### 5.1 流式路线查询

前端主查询走流式接口：

```text
用户提交查询表单
  ↓
App.tsx handleSubmit()
  ↓
searchRoutesStream(payload, onPlan, signal)
  ↓

  ↓

  ↓
```

流式返回 NDJSON snapshot 和 metadata；如果后端捕获到数据源错误，会返回带 `error` 字段的 JSON 行，前端转换为 `ApiError(data_source_unavailable)`。

站点自动补全已从当前 API 范围移除。页面保留手动输入站名；后续补全应由独立 `StationSearchService`、前端本地索引或明确的静态站点 API 承担，不应由 API 层隐式调用 provider。

```text

  ↓
getProviderStatus()
  ↓

  ↓

```

## 7. 领域模型

文件：`backend/app/domain/models.py`。

| 模型                  | 职责                                                                   |
| --------------------- | ---------------------------------------------------------------------- |
| `SeatPrice`           | 席别、价格、余票状态占位                                               |
| `TrainSegment`        | 单段车次，包含车次号、起终站、时刻、历时、价格、来源和更新时间         |
| `RouteQuery`          | 查询条件：出发站、到达站、日期、最大中转次数、最短换乘时间、最大总耗时 |
| `TransferPlan`        | 完整路线方案，包含总价、总耗时、换乘等待、换乘站和车次段               |
| `RouteSearchResponse` | 路线查询响应                                                           |
| `StationMetadata`     | 候选中转站元数据                                                       |

关键约束：

- `TrainSegment.arrive_at` 必须晚于 `depart_at`。
- `RouteQuery.max_transfers` 限制为 `0..2`。
- `SeatPrice.price` 使用 `Decimal`，避免浮点误差。

## 9. 搜索服务架构

搜索入口抽象文件：`backend/app/services/route_search_engine.py`。

搜索引擎工厂文件：`backend/app/services/route_search_engine_factory.py`。

```text
ROUTE_SEARCH_ENGINE 未设置 / online
  → OnlineRouteSearchEngine，即基于 TrainDataProvider 的统一在线 OD 路径搜索

ROUTE_SEARCH_ENGINE=candidate / od-candidate / legacy
  → OnlineRouteSearchEngine，仅作为历史配置兼容别名

ROUTE_SEARCH_ENGINE=time-expanded / time_expanded
  → TimeExpandedRouteSearchEngine，即本地 SQLite 时间扩展图搜索
```

`RouteSearchEngine` 对 API 层只暴露 `source`、`status` 和 `stream_snapshots(query)`。`GET /api/providers/status` 透传当前搜索引擎状态，因此会包含 `search_engine`、`expansion_strategy`、`online_remote_io` 和 `global_optimum_guaranteed` 等字段。

### 9.0 多重搜索架构边界

在线 OD 搜索保留 provider 链路，可使用 `static-with-remote-fallback`。该 fallback 只属于 online 搜索，不属于本地时间扩展图查询。

时间扩展图搜索文件：`backend/app/services/time_expanded_route_search.py`。

当前最小实现从 `train_od_price_snapshot` 读取本地 OD 乘车边，把每条快照记录视为：

```text
from_station at depart_at -> to_station at arrive_at, weight=price
```

`time-expanded` 查询阶段只读本地 SQLite，不调用 `TrainDataProvider.search_segments()`，不调用 `Railway12306PublicPriceProvider`，也不会触发 `static-with-remote-fallback`。本地快照缺失时返回无方案或表现为覆盖不足；不得把静态公布票价宣称为实时有票，也不得宣称当前时间扩展图已有全国完整覆盖。

核心文件：`backend/app/services/route_search.py`。

### 9.1 总体搜索链路

```text
OnlineRouteSearchEngine.stream_snapshots(query)
  ↓
创建请求级 OnlineSearchContext
  ↓
_search_plans(query, context)
  └─ 单一优先队列统一覆盖直达、一换和二换
     max_transfers 只作为路径扩展约束
  ↓
_deduplicate_plans()
  ↓
按 _plan_sort_key() 排序
  ↓
截断到 MAX_RETURNED_PLANS = 10
  ↓
_record_search()
  ↓
单个 final=True StreamSnapshot
```

当前扩展策略标识为 `candidate-station-od`：候选站只决定尝试扩展哪些在线 OD，边在需要时通过 provider 懒加载。该策略受候选召回、缓存、请求预算和 provider 数据覆盖限制，因此 `global_optimum_guaranteed=false`。它不是全国完整铁路图搜索。

### 9.2 统一路径扩展

所有换乘次数共用同一搜索循环：

```text
初始状态(origin, price=0, segments=[])
  → 优先扩展当前累计价格最低的状态
  → 终点始终可作为下一 OD 目标
  → 未达到 max_transfers 时追加候选扩展站
  → 按 min_transfer_minutes 过滤不可衔接车次
  → 按 max_total_duration_minutes 过滤完整方案
  → 通过 Pareto frontier 剪枝受支配状态
```

搜索以累计票价作为队列优先级，当前等价 Uniform Cost Search。历史最低票价只用于候选排序和采集优先级，不作为正确性剪枝 lower bound。

历史实现曾为 `max_transfers < 2` 保留直达/一换专用分支，并为 `max_transfers >= 2` 调用 `CheapestPathSearcher`。这套结构源自增量兼容，造成重复逻辑和行为分叉，现已删除。

### 9.3 Pareto frontier

`OnlineSearchParetoFrontier` 以 `(当前站, 中转次数)` 为 key。只有已有状态同时满足：

```text
已有累计价格 <= 当前累计价格
且已有到达时间 <= 当前到达时间
```

时才剪枝。这样保留“更贵但更早到达”的状态，避免误剪可能形成低价后续路径的方案。

### 9.4 排序规则

主排序目标始终是最低总价：

```text
1. total_price
2. 换乘等待舒适性惩罚
3. 换乘次数
4. 总耗时
```

换乘等待舒适区间为 `30~120` 分钟。等待过短或过长只影响同价方案排序，不改变最低价主目标。

### 9.5 请求预算、并发和缓存链路

`_search_segments()` 查询顺序：

```text
1. 内存 TTL 缓存
2. SQLite OD 持久化缓存（仅当 ROUTE_SEGMENT_CACHE_DB 启用）
3. provider
4. 写回内存缓存
5. 写回 SQLite OD 缓存（若启用）
```

并发控制：

- `max_remote_queries`：单次搜索最大 OD 请求数。
- `max_concurrent_remote_queries`：provider 查询并发上限。
- `remote_query_interval_seconds`：非 Mock provider 默认请求间隔。

诊断信息保存在 `SearchDiagnostics`：远程请求数、内存缓存命中、SQLite 缓存命中、已扩展 OD 目标、失败 OD 目标、完整方案价格界剪枝和 Pareto 剪枝次数。

## 10. 候选中转站生成

文件：`backend/app/services/transfer_candidates.py`。

核心对象：`CandidateTransferStationGenerator`、`StationMetadataRepository`、`CandidateTransferConfig`。

当前逻辑：读取出发站和到达站元数据，计算 OD 球面距离，按 corridor 筛选走廊内站点，剔除过近端点站，按人工换乘先验、中心性、走廊偏离等排序，返回 Top N 候选站。站点元数据缺失时 fallback 到人工维护的换乘枢纽列表。

重要边界：候选生成是启发式召回，不是正确性剪枝。铁路票价并不存在稳定的“低价站点”概念，站点价值来自换乘枢纽、径路分叉、车型切换或铁路通道属性。后续应支持用户控制候选数量、绕行范围和搜索策略，避免 `东莞 -> 拉萨` 这类需要绕行到进藏通道节点的方案被地理走廊直接剪掉。

## 11. 缓存与持久化

### 11.1 内存 TTL 缓存

文件：`backend/app/services/cache.py`。

`TtlCache` 是进程内缓存，key 为：

```text
provider:date:from_station:to_station
```

### 11.2 SQLite OD 查询缓存

`SqliteOdCache` 通过环境变量启用：

```text
ROUTE_SEGMENT_CACHE_DB
ROUTE_SEGMENT_CACHE_TTL_SECONDS
```

用于缓存 provider 的 OD 查询结果，减少重复远程请求。命中后会回填内存缓存，并且不增加 `remote_query_count`。

### 11.3 SQLite 静态票价库

文件：`backend/app/services/static_price_repository.py`。

核心表：

| 表                         | 职责                                                   |
| -------------------------- | ------------------------------------------------------ |
| `station_snapshot`         | 预留保存站点名称、电报码、拼音和抓取时间等站点快照信息 |
| `od_public_price_snapshot` | 保存某日期、某 OD、某车次、某席别的公布票价            |
| `od_min_price_snapshot`    | 保存某日期、某 OD 的最低价聚合结果                     |
| `train_od_fare_edge`       | 保存不绑定 service_date 的时间扩展图基础边             |
| `crawl_job`                | 保存一次刷新任务的整体状态                             |
| `crawl_task`               | 保存刷新任务内每个 OD 的执行状态                       |

说明：当前代码已经在 `SQLiteStaticPriceRepository._ensure_schema()` 中创建 `station_snapshot` 表；但静态票价刷新和查询主链路仍以 OD 票价快照为核心，站点快照的完整写入和使用闭环仍属于后续扩展。

`train_od_fare_edge` 由全量快照爬虫或导入流程写入，不保存 `service_date`，只保存车次、站序、相对到发时刻、day offset、席别和价格。`TimeExpandedRouteSearchEngine` 在线查询时优先读取该表，并按 `query.date + 0/1/2` 展开为实际时间边。展开出来的边不是都能当首段：`_can_take` 要求首段必须在查询当天出发，次日边只能作为换乘的后续段，否则同一趟车会对同一个查询变出多天方案。返回前还会调用 `_keep_best_plan_per_train_sequence` 按"车次序列"去重，同一组车次只保留排序最优的一条，避免同一路线的多个日期变体占满 `MAX_RETURNED_PLANS`。若该表无数据，保留读取旧 `train_od_price_snapshot` 的兼容路径。

全量快照爬虫脚本：`backend/scripts/crawl_time_expanded_full_snapshot.py`。

职责：

1. 调用 `getTrainName(date)` 获取并按 `train_no` 去重车次。
2. 调用 `queryTrainInfo/query` 获取单车经停序列。
3. 生成同车所有 `i < j` OD 票价任务，可用参数限制规模。
4. 调用 `queryAllPublicPrice` 获取公布票价并筛选目标车次。
5. 将席别价格展开写入 `train_od_fare_edge`。
6. 创建 `crawl_full_snapshot_train_task` 和 `crawl_full_snapshot_price_task`，支持 `--resume` 重置遗留 running，支持 `--retry-failed` 重置 failed。

该脚本属于离线长任务，不应放入 FastAPI 请求链路。

```text
data/refresh_od.csv
  ↓
backend/scripts/refresh_static_prices.py
  ↓
data/static_prices.sqlite3
  ↓
LocalStaticPriceProvider
  ↓
OnlineRouteSearchEngine 后续搜索优先本地命中
```

### 12.1 遥测导出脚本

文件：`backend/scripts/export_refresh_od_from_telemetry.py`。

能力：从 `search_runs` 聚合高频查询 OD；从 `transfer_station_hits` 展开 `A -> T` 和 `T -> B`；合并重复 OD；输出 `origin,destination,priority,reason` CSV。

### 12.2 静态票价刷新脚本

文件：`backend/scripts/refresh_static_prices.py`。

能力：读取 OD CSV、调用远程 provider、限速、部分失败不中断整体任务、写入 `crawl_job` / `crawl_task`、写入静态票价库。

脚本读取 `origin/destination/priority/reason` 四列。`priority` 缺省为 100；缺少该列、单元格为空或值不是整数时回落默认值。执行前按 `priority` 升序排序，再应用 `--limit`，因此 `--limit N` 截取的是优先级最高的 N 个 OD。`reason` 目前只随 CSV 读入，尚未落库。失败 OD 报告导出仍是后续增强。

### 12.3 静态票价库诊断脚本

文件：`backend/scripts/inspect_static_prices.py`。

能力：查看静态库整体覆盖；查询指定日期和 OD 的车次数、席别覆盖、最低价、最低价车次、最低价席别和更新时间。

## 15. 典型运行链路

### 15.1 Mock 模式

```text
TRAIN_DATA_PROVIDER 未设置或 mock
  ↓
OnlineRouteSearchEngine
  ↓
MockTrainDataProvider
  ↓
返回固定样例中的直达和一换方案
```

### 15.2 12306 公布票价模式

```text
TRAIN_DATA_PROVIDER=12306-public-price
  ↓
OnlineRouteSearchEngine 请求 OD
  ↓
内存缓存 / SQLite OD 缓存
  ↓ 未命中
Railway12306PublicPriceProvider
  ↓
12306 公布票价接口
  ↓
解析为 TrainSegment
  ↓
缓存并返回搜索方案
```

### 15.3 静态票价库只读模式

```text
TRAIN_DATA_PROVIDER=static-price
STATIC_PRICE_MODE=static-only
  ↓
OnlineRouteSearchEngine 请求 OD
  ↓
LocalStaticPriceProvider
  ↓
SQLiteStaticPriceRepository.query_segments()
  ↓
有数据则返回，无数据则返回空列表
```

### 15.4 静态票价库 fallback 模式

```text
TRAIN_DATA_PROVIDER=static-price
STATIC_PRICE_MODE=static-with-remote-fallback
  ↓
先查 SQLite 静态库
  ↓ 未命中或过期
调用 12306 公布票价 provider
  ↓
远程结果写回 SQLite
  ↓
返回本次结果
```

### 15.5 遥测反哺刷新闭环

```text
启用 SEARCH_TELEMETRY_DB
  ↓
用户多次搜索
  ↓
search_runs 和 transfer_station_hits 累计数据
  ↓
export_refresh_od_from_telemetry.py 导出 refresh_od.csv
  ↓
refresh_static_prices.py 刷新静态票价库
  ↓
后续 static-price 查询减少远程 I/O
```

### 15.6 时间扩展图本地搜索模式

```text
ROUTE_SEARCH_ENGINE=time-expanded
TIME_EXPANDED_GRAPH_DB=...
  ↓
TimeExpandedRouteSearchEngine
  ↓
SQLiteStaticPriceRepository.query_train_od_prices()
  ↓
读取 train_od_price_snapshot
  ↓
本地 Dijkstra/Uniform Cost 展开乘车边
  ↓
返回直达或中转方案
```

该链路在线阶段无远程 I/O；如果 SQLite 中没有覆盖相关日期、站点和车次边，则返回无方案。

## 17. 当前边界和后续演进

当前边界：

1. `12306-public-price` 依赖非公开稳定接口，存在失败、限流和字段变化风险。
2. 静态票价库表示公布票价或历史观测票价，不表示实时余票。
3. 时间扩展图搜索当前依赖本地 `train_od_price_snapshot` 覆盖，不代表全国完整覆盖。
4. 时间扩展图搜索只表达静态公布票价快照，不表达实时余票。
5. 当前二换搜索的启发函数为 `0`，等价 Uniform Cost Search。
6. 历史最低价不是安全 lower bound，不能用于硬剪枝。
7. SQLite 适合当前单机 MVP；多实例并发写或多人共享场景后再考虑 PostgreSQL。
8. 刷新脚本应作为独立脚本、定时任务或 worker 执行，不应放入 FastAPI 请求链路。
9. 前端当前固定查询一次中转，尚未暴露最大中转次数配置。

后续演进：

1. ~~增强~~ `refresh_static_prices.py`，~~读取并使用~~ `priority/reason`（已完成：读取 `priority` 并按升序刷新；`reason` 仅读入未落库）剩余工作：输出失败OD报告。
2. 扩充 `data/seed_od.csv` 和由遥测导出的 `refresh_od.csv`，提高静态票价库覆盖率。
3. 前端更明确展示 `mock`、`12306-public-price`、`static-price` 的数据来源和更新时间。
4. 增加静态库覆盖率、搜索遥测、缓存命中和远程请求下降情况的诊断能力。
5. 建立更完整的站点和车次经停知识库。
6. 将刷新任务从手动脚本升级为定时任务或独立 worker。
7. 在能证明不高估的前提下设计 A* lower bound。
