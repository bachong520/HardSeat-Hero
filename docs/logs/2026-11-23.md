### 二、真实接口长什么样

三步，全部匿名，没有登录、没有 token、没有签名：

1. `GET otn/resources/js/framework/station_name.js` 拿站名→电报码（北京→BJP、上海→SHH）；
2. `GET otn/view/queryPublicIndex.html` 先访问一次拿基础 cookie；
3. `GET otn/leftTicketPrice/queryAllPublicPrice?leftTicketDTO.train_date=...&from_station=BJP&to_station=SHH&purpose_codes=ADULT`。

返回 `{status, data:[{queryLeftNewDTO:{...}}]}`，价格字段是**角**且带前导零
（`ze_price: "07950"` → 795 元），`parse_price` 除以 10。七个席别字段：
`swz_price` / `zy_price` / `ze_price` / `yz_price` / `yw_price` / `rw_price` / `gr_price`。

排障插曲：探测脚本一开始一直报

```
URLError: <urlopen error [SSL: CERTIFICATE_VERIFY_FAILED]
certificate verify failed: unable to get local issuer certificate (_ssl.c:1010)>
```

证书本身没问题（CFCA 签发、`*.12306.cn`、2027-05 到期），httpx 与 `ssl` 默认上下文都能
握手成功。真因是机器上开着「畅课课程签到监控」——一个常驻脚本接管了系统流量/证书。
关掉它立刻恢复。**教训：跑采集前先关掉这类常驻监控脚本，否则会误判成接口过期。**

实测：北京→上海 2026-11-27 共 52 趟车；G531 商务座 2782 元 / 一等 1272 / 二等 795。

所以判定写的是「**通过（有条件）**」——控制流（认领、租约、重试、幂等）证明了，
但数据没落地，明天接口一变什么都留不下。这是 `docs/plans/云函数worker真实接口PoC报告_2026-11-23.md`

### 四、响应摘要落库

三层管道（schema 字段、`CloudTaskResponseSummary`、两个 repository）早就通了，
**只有生产者 provider 从没填过**。补了两处：

- `ProviderRowsResult` 新增 `response_excerpt`，worker 透传进 `CloudTaskResponseSummary`；
- `providers.build_response_excerpt(rows, *, max_chars=8000)`，输出统一信封：

```json
{"total_rows": 335, "truncated": true, "rows": [...]}
```

用信封而不是裸数组，是因为截断后「335 行里只装了 40 行」和「本来就只有 40 行」
无法区分。截断按**整行**切，绝不切半行（`if used + extra > budget and kept: break`，
`and kept` 保证至少留一行）。

job 2 真跑：`p50=634ms p95=697ms succeeded=3`，三条摘要 7720 / 7726 / 7389 字节，
全部 `truncated: true`，`total_rows` 52/73/335 完整。

**8 KB 装不下 335 趟车**——摘要只够验证链路，不够当合并数据源，肉眼看不出漏了多少。

### 五、阶段 6 离线合并

新增 `backend/scripts/merge_cloud_responses_to_edges.py`：读
`crawl_cloud_station_od_response.response_excerpt` → 拆信封 → 每行 `queryLeftNewDTO`
转成 `TrainOdFareEdge` → `upsert_train_od_fare_edges` 写进 `data/graph_from_cloud.sqlite3`
（被 `.gitignore` 挡住）。

**踩到的建模陷阱：站名和城市名不是一回事。** 任务是「北京→上海」，响应里的
`from_station_name` 却是「北京南」「上海虹桥」。第一版直接用车站在建节点，结果
12 趟直达车里只有 1 趟恰好叫「北京→上海」，搜索只出 1 条方案。改成**用任务的城市名
作节点、车站名写进 `raw_hash` 留痕**后，立刻变成 10 条。现有的 `graph_from_od.sqlite3`
（107,923 条边）本来就是城市级粒度，这样也才一致。

代价是丢失「这趟车具体从北京南还是北京站发车」，记为遗留。

合并结果：3 条响应 → 105 条边（去重后 102 条），引擎搜「北京→上海 2026-11-27」
mt=0 得 10 条直达（795 元 4h43m 起），mt=1 得 10 条含 689.5 元经南京南的换乘方案。
从云端请求到搜索结果的闭环第一次真正连上。

但图是**残缺**的：12/52、12/73、11/335 行。所以这是链路验证，不是正式数据。

### 六、job 收尾（本次的 C）

缺陷：worker 跑完一批就退出，`crawl_cloud_job.status` 永远停在 `running`。
新增 `finalize_job_if_finished(job_id, *, now)`，在 `run_cloud_price_worker` 末尾
（非 dry_run）调用，一个事务里数状态、判断、更新，顺手把 7 个计数字段刷成真实值。

判定规则：

| 情况 | 结果 |
| --- | --- |
| 还有 `pending` / `retry_wait` / `leased` | 不动，返回 `None` |
| 全清空、无死信无失败 | `succeeded` |
| 全清空、有 `dead_letter` / `failed` | `failed` |
| job 已是 `cancelled` 或已被别人收尾 | `UPDATE` 命中 0 行，不覆盖 |

「有死信就判 failed」是这一天里唯一有争议的选择：宁可显眼，也不要让「跑了 1 万条、
死了 3 条」看起来和全成功一样。若要改成按死信率判定，得先给 schema 加状态值。

### 八、事故与教训：测试库指错，PoC 数据被清

为了验证收尾的 SQL，把 `CLOUD_CRAWL_TEST_DATABASE_URL` 指向了 **`hardseat_cloud`
（和真实数据同一个库）**。测试夹具开头是：

```python
conn.execute("DELETE FROM crawl_cloud_dead_letter")
conn.execute("DELETE FROM crawl_cloud_station_od_response")
conn.execute("DELETE FROM crawl_cloud_station_od_task")
conn.execute("DELETE FROM crawl_cloud_job")
```

于是 job 1、job 2 和那 3 条响应被删掉了。`data/graph_from_cloud.sqlite3` 是删之前
写好的，不受影响。

补救：建 `hardseat_cloud_test`，PG 测试只指向它；真实库里测试残留的 `job 22 (running)`
已连同 2 个任务一起删除，现在只剩 job 23。想恢复真实 PoC 数据，重跑
`prepare_cloud_poc_job.py --write` 与 worker 两条命令即可（需联网，3 个请求）。

教训：**跑任何带清理逻辑的测试前，先看夹具，再确认 DSN 指向哪个库。**
