# 开发日志 2026-11-14

## 2026-11-14 离线搜索：真实数据下的性能优化

### 背景

2026-11-12 把 `od_public_price_snapshot`（187,231 行）转成基础边后，离线图从 875 条涨到 107,923 条。用 `data/graph_from_od.sqlite3` 实测，北京出发的查询直接卡死：

| 场景 | 改前耗时 |
| --- | --- |
| 北京 -> 上海，直达 | 6.7 s |
| 北京 -> 上海，1 次换乘 | 超过 120 s 未返回 |
| 北京 -> 上海，2 次换乘 | 超过 240 s 未返回 |
| 南京 -> 上海，1 次换乘 | 2.2 s |

同时把 `MAX_RETURNED_PLANS` 临时放开后测到一个关键数字：北京 -> 上海 1 次换乘会生成 **18,953 个方案**，而函数只返回 10 个。也就是说 99.95% 的搜索是不必要的。

### 一、状态去重键从「完整路径」改为「到达状态」

原实现的去重键包含整条走过的路径：

```python
state_key = (
    state.station,
    state.arrive_at,
    state.total_price,
    tuple((segment.train_no, segment.from_station, ...) for segment in state.segments),
)
```

等于「每换一种车次组合就是一个新状态」。北京出站 4,744 条边，按 0/1/2 天展开约 1.4 万个起点，排列组合会爆炸。

改为按 `(车站, 到达时刻)` 保留最便宜的一条：

```python
slot = (state.station, state.arrive_at)
known_price = best_price_per_arrival.get(slot)
if known_price is not None and price >= known_price:
    continue
best_price_per_arrival[slot] = price
```

正确性依据：票价为非负数。两条路径若在同一时刻到达同一车站，后半程的可行集合完全相同，已花更多钱的那条不可能反超，因此剪掉是安全的。这是 Dijkstra 的标准状态定义，原实现多带了路径维度。

### 二、候选车次从「全量扫描」改为二分定位

原实现对每一站遍历全部出站边：

```python
for edge in edges_by_station.get(state.station, []):
```

改为按 `depart_at` 排序后用 `bisect` 圈出时间窗：

```python
if state.arrive_at is None:
    earliest = datetime.combine(query.date, time.min, tzinfo=timezone.utc)
    latest = earliest + timedelta(days=1)
else:
    earliest = state.arrive_at + timedelta(minutes=query.min_transfer_minutes)
    latest = state.arrive_at + timedelta(minutes=query.max_transfer_minutes)
start, end = bisect_left(departures, earliest), bisect_right(departures, latest)
```

这里依赖 2026-11-12 新增的 `max_transfer_minutes`：有等待上限，时间窗才是有限区间，二分才有意义。`_can_take` 仍保留作二次校验。

### 三、攒够前 10 名后提前结束

方案是随扩展按价格单调不减地生成的：堆每次弹出当前最便宜的状态，新方案价格 = 已花价格 + 本段票价，必然不低于当前弹出价格。因此维护一个只装 10 个价格的负值堆，堆顶就是第 10 名的价格：

```python
if len(plan_price_heap) >= MAX_RETURNED_PLANS and price > -plan_price_heap[0]:
    break
```

比较用严格大于而非大于等于：价格相同但耗时更短的方案仍需展开，否则会改变并列时的排序结果。

### 四、验证

同一份数据、同一天（2026-07-18）：

| 场景 | 改前 | 剪枝 + 二分 | 再加提前结束 |
| --- | --- | --- | --- |
| 北京 -> 上海，1 次换乘 | 超时 | 6.06 s | 3.85 s |
| 北京 -> 上海，2 次换乘 | 超时 | 11.25 s | 5.17 s |
| 南京 -> 上海，1 次换乘 | 2.2 s | — | 2.06 s |

三次结果一致，前三个方案均为 `156.5 元直达`、`163.0 元 2 段`、`163.0 元 2 段`。

当前耗时构成（北京 -> 上海 1 次换乘，合计 3.85 s）：

```text
_load_edges   1.85 s   读 107,923 条基础边并按 0/1/2 天展开成 323,769 条
搜索          2.00 s   已剪到只探索必要状态
```

全量测试：`256 passed, 7 skipped, 1 warning in 15.41s`，与改动前一致。

### 五、遗留

- 瓶颈已转移到数据加载：`_load_edges` 每次查询都重新读 10 万条边并展开成 32 万条对象。可选方向是按 (provider, 日期) 缓存展开结果（省 1.85 s，代价约 150 MB/日期），或把基础边预计算成按站索引的独立表。当前 3.85 s 对原型够用，暂不处理。
- 提前结束依赖「方案按价格单调生成」这一性质，若将来允许负权重或允许先返回价格更高但更快的方案，该剪枝必须重新评估。
- 状态剪枝只保留 `(车站, 到达时刻)` 下最便宜的一条，因此同到达时刻、价格相同但车次不同的变体会在搜索阶段合并，最终仍由 `_keep_best_plan_per_train_sequence` 做一次去重。若将来需要"同一时刻给出多种车次组合"，需要把车次序列重新纳入状态。
