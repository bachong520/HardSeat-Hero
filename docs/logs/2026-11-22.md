# 开发日志 2026-11-22

## 2026-11-22 浏览器验收：白屏修复与结果排序切换

### 背景

2026-11-14 的剪枝与提前结束后，离线引擎已能在秒级返回结果（北京 -> 上海 1 次换乘 3.85 s）。今天第一次把前端 `vite` 和后端 `uvicorn` 同时跑起来，在浏览器里用 `data/graph_from_od.sqlite3` 查「北京 -> 上海，2026-11-25，最多 1 次换乘」，从真实使用路径上暴露了两个问题：

1. 页面打开后瞬间白屏，看不到任何方案；
2. 结果只有一种呈现顺序，而「同价不同等待」的方案挤在一起，用户无从比较。

### 一、白屏：可选链只保护一层

`ProviderDiagnostics.tsx` 的写法是：

```tsx
{providerStatus?.last_diagnostics.memory_cache_hit_count ?? "-"}
```

`?.` 只保护紧邻它的那个对象。`providerStatus` 存在（后端已经返回），所以可选链放行，接着执行 `.last_diagnostics` 得到 `undefined`，再取 `.memory_cache_hit_count` 就抛：

```text
TypeError: Cannot read properties of undefined (reading 'memory_cache_hit_count')
```

React 19 对未捕获的渲染异常没有内置错误边界，会直接卸载整棵组件树，于是页面从「渲染完成」直接变成空白。第一次渲染时 `providerStatus` 还是 `null`，`?.` 生效，所以用户看到的顺序是「闪一下 -> 白屏」，而不是「一直白」。

类型系统没能拦住，因为 `frontend/src/lib/api.ts` 当时把它声明成必填：

```ts
last_diagnostics: SearchDiagnostics;
```

**类型描述的是「我们以为后端会返回什么」，写错了就等于关掉了编译器的检查。**

前端修法（两层）：

```ts
// api.ts
last_diagnostics?: SearchDiagnostics;

// ProviderDiagnostics.tsx
{providerStatus?.last_diagnostics?.memory_cache_hit_count ?? "-"}
```

### 二、两个引擎的状态载荷契约

白屏的直接原因是字段缺失，更深一层原因是 `/api/providers/status` 的响应结构在两个引擎之间分叉了：

| 字段 | 在线引擎 | 离线引擎（改前） |
| --- | --- | --- |
| `provider` / `search_engine` / `status` / `online_remote_io` | 有 | 有 |
| `expansion_strategy` | 有 | 无 |
| `global_optimum_guaranteed` | 有 | 无 |
| `transfer_candidate_enabled` | 有 | 无 |
| `max_remote_queries` / `max_concurrent_remote_queries` | 有 | 无 |
| `last_remote_query_count` | 有 | 无 |
| `last_diagnostics` | 有 | 无 |

`TimeExpandedRouteSearchEngine.status` 补齐为同一套 12 个键。离线引擎不发起远程请求、也没有候选站扩展阶段，因此相关计数一律为 0：

```python
"expansion_strategy": "time-expanded-graph",
"global_optimum_guaranteed": False,
"transfer_candidate_enabled": False,
"max_remote_queries": 0,
"max_concurrent_remote_queries": 0,
"last_remote_query_count": 0,
"last_diagnostics": SearchDiagnostics().as_dict(),
```

补字段只是让当前调用方不崩，真正防复发的是这条契约测试：

```python
assert set(offline_engine.status) == set(online_engine.status)
assert set(offline_engine.status["last_diagnostics"]) == set(
    online_engine.status["last_diagnostics"]
)
```

它第一次运行就抓到了漏写的 `global_optimum_guaranteed`。之后任一引擎增删字段而未同步，CI 会直接失败。

### 三、结果排序切换

后端返回的顺序是 `(总价, 换乘次数, 换乘等待, 总时长)`，这是作者调过的综合偏好，但同一批结果换个视角看结论会变。因此把排序搬到前端，对已返回的方案做重排，不重新请求后端：

| 模式 | 比较键 |
| --- | --- |
| 默认 | 保持后端顺序 |
| 最低价 | 总价 -> 总时长 -> 换乘次数 |
| 最快 | 总时长 -> 总价 -> 换乘次数 |
| 少等待 | 换乘等待 -> 总价 -> 总时长 |
| 最早发车 | 第一段出发时刻 -> 总价 -> 总时长 |

实现要点：

- `sortPlans` 是纯函数（`frontend/src/features/route-search/sortPlans.ts`），先拷贝再排序，不就地修改 React state 中的数组。
- 组件里用 `useMemo(() => sortPlans(plans, sortMode), [plans, sortMode])`，因为 `sortPlans` 每次返回新数组，不加缓存会在渲染期反复触发重算。
- 比较器用 `a || b || c` 串联实现多级排序，等价于 SQL 的 `ORDER BY a, b, c`。
- 「最早发车」比较的是 `new Date(depart_at).getTime()` 得到的绝对时刻，而不是钟点字符串：`depart_at` 是 UTC 时间戳（`19:59` 北京时间实际存为 `11:59Z`），跨天方案只有比较绝对时刻才正确；解析失败时返回 `Number.POSITIVE_INFINITY` 排到最后，避免整表排序抛异常。
- 卡片的 key 从 `${total_price}-${index}` 改为 `车次@发车时刻`。带下标的 key 在换序时会让 React 误认为换了一批卡片而重建 DOM。

界面用一排圆角按钮而非下拉菜单：5 个短标签、且用户会反复切换对比，分段控件的「一眼看全 + 一次点击」优于下拉菜单的「省空间 + 多一次点击」。若选项超过 7 个或标签变长，再改为下拉菜单。

### 四、验证

真实数据（`data/graph_from_od.sqlite3`，北京 -> 上海，2026-11-25，最多 1 次换乘，共 10 个方案）下五种排序的前三名：

| 排名 | 默认 / 最低价 | 最快 | 少等待 | 最早发车 |
| --- | --- | --- | --- | --- |
| 1 | 156.5 直达 18h46m 等 0 | 156.5 直达 | 156.5 直达 | 163.0 K887+1461 17:32 发 |
| 2 | 163.0 1461+K233 等 35m | 163.0 T57+1461 19h12m | 163.0 1461+K233 等 35m | 163.0 T57+1461 19:33 发 |
| 3 | 163.0 1461+K849 等 41m | 163.0 1461+K849 | 163.0 1461+K849 等 41m | 156.5 直达 19:59 发 |

- 前端：`corepack pnpm exec tsc -b` 通过。
- 后端：`257 passed, 7 skipped, 1 warning in 15.59s`（2026-11-14 基线 256，新增 1 条契约测试）。
- 浏览器：`http://localhost:5173/` 搜索成功，五个排序按钮切换正常，状态面板不再白屏。

### 五、遗留

- 这份数据 10 个方案里有 9 个是 163.0 元硬座，价格高度集中，导致「最低价」与「最快」给出相同顺序；排序切换的差异要等高铁 / 卧铺等多席别数据进来才会明显。
- 排序只作用于后端已返回的前 10 条，不是全量排序。若将来放开返回条数，需要重新考虑前端是否还适合承担排序。
- 状态面板对离线引擎会显示「缓存命中 0 / 已扩展 OD 目标 -」等无意义行，可按引擎类型裁剪显示。
- 前端目前没有测试框架（`package.json` 只有 `dev` / `build`），`sortPlans` 是纯函数，是最适合补单测的入口；要补需先引入 `vitest`。
- 开发环境已知问题：代码编辑器写入文件时会在源码目录留下临时目录，`vite` 的文件监听器遇到被锁定的文件会以 `EBUSY` 退出，改完前端文件后重启 dev server 即可。
