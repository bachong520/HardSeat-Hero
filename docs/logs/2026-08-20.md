# 开发日志 2026-08-20

## 在线搜索行为回归排查与修复

### 现象

在线搜索引擎重构后，东莞到厦门的最低价方案从重构前的赣州中转、约 `127` 元，变为惠州中转、约 `200` 元。同时观察到在线 OD 请求预算容易打满，怀疑请求扩展过多导致最优方案未被访问。

### 根因

统一优先队列搜索到达第一个中转站后，`OnlineSearchState.transfer_count` 的计算为 `len(segments) - 1`。对于已经走完第一段车程的状态，该值仍为 `0`。当 `max_transfers=1` 时，`_next_expansion_stations()` 因此错误地继续扩展其它候选站，产生候选站之间的无效 OD 请求：

```text
东莞 -> 候选站
候选站 -> 其它候选站
```

这些请求不能形成合法的一换方案，但会消耗 `max_remote_queries`。在候选站较多时，预算可能在搜索到赣州第二程之前耗尽。该问题属于换乘层数和已行驶车段数量的边界混淆，不是赣州候选排序错误。

### 修复

- 修改 `backend/app/services/route_search.py`：
  - 候选站扩展条件改为 `len(state.segments) < query.max_transfers`。
  - 已达到最大换乘次数的状态只允许查询终点，不再查询其它候选站。
  - 保留二换场景中从第一个候选站扩展到第二个候选站的能力。
- 修改 `backend/tests/test_route_search.py`：
  - 新增预算敏感的一换 provider，构造“惠州第一程更便宜、赣州总价更低”的场景。
  - 断言预算受限时仍返回赣州 `127` 元方案。
  - 断言不产生候选站之间的 OD 请求。
  - 断言预算不会因无效扩展被打满。

## 在线搜索服务模块拆分

### 背景

`backend/app/services/route_search.py` 同时包含在线搜索状态、Pareto 剪枝、方案构造、结果排序、缓存序列化等多个职责，单文件代码量接近 500 行，维护成本较高。

### 修改

- 新增 `backend/app/services/route_search_models.py`：集中搜索诊断、搜索上下文、路径状态和 Pareto Frontier。
- 新增 `backend/app/services/route_search_plans.py`：集中方案构造、排序、换乘等待惩罚、时长过滤和去重。
- 新增 `backend/app/services/route_search_serializers.py`：集中车次段缓存的 JSON 序列化和反序列化。
- 修改 `backend/app/services/route_search.py`：保留搜索编排、候选站扩展、OD 查询、缓存和遥测流程；通过导入和委托使用拆分模块，并保留原有名称兼容现有测试。
- 主文件从约 `489` 行减少到 `375` 行。
