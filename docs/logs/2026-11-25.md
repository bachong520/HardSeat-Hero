# 开发日志 2026-11-25

## 2026-11-25 车站到城市映射与完整响应体落库

### 背景

11-23 的 PoC 跑通了，但留下两个硬伤，两个都指向同一件事：**数据能进来，但进得不全、进得不对**。

1. 摘要装不下。`response_excerpt` 上限 8000 字符，一条 335 趟车的 OD 只装得下 11 行。合并时用的就是这份截断数据，边数是 33 条——不是真实规模，是"前 12 行的规模"。
2. 站名不是城市名。任务写的是「北京→上海」，响应里每趟车写的是「北京南→上海虹桥」。第一版拿车站名建图，105 条边写进去，搜「北京→上海」只出 1 条方案。

所以顺序是：先修粒度（B），再修完整性（A）。粒度错误会让"数据全了"这件事变得没意义——全了也搜不到。

### 一、B：车站到城市的映射

**先找现成的，不要先写新的。** 仓库里已经有 `backend/app/data/station_metadata.csv`，1,918 个站，列是 `name,telecode,latitude,longitude,centrality_score,province,city,railway_bureau,station_type`。只是 `backend/app/services/transfer_candidates.py:109` 的 `load_station_metadata()` 只取了名字、电报码、经纬度和中心度，`province`/`city` 两列被丢掉了。

发现一个容易踩的细节：**这份表的 `city` 列对直辖市填的是区名**。83 行以"区/县"结尾，其中北京 23、上海 12、天津 12、重庆 26。直接拿 `city` 当归一结果，`北京南` 会变成「丰台区」。所以规则是：

```python
province in {"北京", "上海", "天津", "重庆"} and province or city
```

归一后是 316 个城市。`od_public_price_snapshot` 的 187 个站名 100% 命中这份测绘表。

新增 `backend/app/domain/station_city.py`：

| 名字 | 作用 |
| --- | --- |
| `MUNICIPALITIES` | 四个直辖市的集合 |
| `normalize_city(province, city)` | 直辖市取省名，其余取城市名 |
| `load_station_city_map(path=...)` | `@lru_cache` 读 CSV，文件缺失返回 `{}` |
| `city_of_station(name, mapping=None)` | 站名 → 城市，查不到返回 `None` |

`merge_cloud_responses_to_edges.py` 相应改造：

- 节点解析变成 `city_of_station(dto_station) or city_of_station(task_station) or dto_station`——先按响应里的站名查，查不到退回任务里的城市名，再查不到就原样用。
- 新增 `--granularity {city,station}`，默认 `city`。
- 映射不到的站名会在报告末尾列出来。

`backend/tests/test_station_city.py` 8 个测试，其中两个是特意挑的：`北京南→北京`（直辖市规则）、`虎门→东莞`（必须靠 `city` 列才对，`name` 里没有"东莞"两个字）。

**验证**：job 24 真跑（1 个任务，759ms），merge 出 33 条城市级边。引擎搜「北京→上海」得 10 个方案（795 元 / 283 分）。同一批数据按车站粒度写成 `12306-public-price-station`，搜「北京南→上海虹桥」得 9 个方案——少的那趟是从北京站发的，符合预期。两种粒度能共存，因为基础边主键带 provider。

### 二、A：完整响应体落库

结论先说：**不需要对象存储**。实测一条 335 趟车的 OD，完整信封是 213,547 字符，PostgreSQL 的 TEXT 上限 1 GB，放得下几百条这样的数据。

改动是把已有的三层管道补齐到最后一环：

| 文件 | 改动 |
| --- | --- |
| `backend/app/cloud_crawl/providers.py` | `build_response_excerpt` 抽出公共的 `_build_envelope(rows, *, max_chars)`；新增 `build_response_body(rows)`（`max_chars=None`，永不截断）；provider 返回时同时带上 body 与 excerpt |
| `backend/app/cloud_crawl/models.py` | `CloudStationOdResponse` 与 `CloudTaskResponseSummary` 各加 `response_body: str \| None = None` |
| `backend/app/cloud_crawl/worker.py` | `ProviderRowsResult` 加 `response_body`，`_process_task` 透传进响应摘要 |
| `backend/app/cloud_crawl/repository.py`、`postgres_repository.py` | 内存实现与 PostgreSQL INSERT 都加上该列 |
| `backend/app/cloud_crawl/postgres_schema.sql` | CREATE 里加列，文件尾追加 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` |

**为什么两档并存而不是只留完整版**：摘要的价值是"人一眼能看懂、报告里能贴"，213 KB 的 JSON 贴不进报告。完整版的价值是"合并的数据源"。两者用途不同，都留着，但要在代码里明确谁是谁：

```python
body = response.get("response_body")
payload = body or response["response_excerpt"]
source = "body" if body else "excerpt"
```

报告里每条任务多一个 `payload_source` 字段。回退到摘要时 `truncated` 会变成 `true`，报告会打印「以下任务库里只有摘要、没有完整响应体，合并用的数据是被截断的」——**让降级可见**，而不是悄悄少一半数据。

一个 schema 细节：`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，所以升级必须单独写 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`。两个库（`hardseat_cloud`、`hardseat_cloud_test`）都跑了一遍 `init_cloud_crawl_postgres.py`，验证都是 14 列。

### 四、遗留问题

1. **测绘表对新建车站有缺口**。这次有 3 个站名映射不到城市：`上海松江`、`北京丰台`、`练塘`。它们都在 12306 上有车，只是这份表没收录（或者是名字对不上，比如表里可能叫「松江」「丰台」）。需要补别名表，或者改成"映射不到就查 12306 的站名接口"，不能长久靠回落。
2. **完整响应体没有大小上限**。现在信任 provider 返回多少就存多少。理论上一条 OD 也可能是几 MB（比如全国所有车次），需要加一个硬上限 + 超限时记 dead-letter，而不是把库撑爆。
3. **合并仍以 job 为单位**。跨 job 的同一条 OD 不会合并去重，靠基础边主键覆盖。同一个 crawl_date 跑两次会是同一个结果（幂等），不同日期则是覆盖——这一点和 `train_od_fare_edge` 的语义（描述"每天跑这个区间"）一致，但需要在文档里写清楚，否则以后有人按日期分别合并会困惑。
4. **城市粒度会合并同城多站**。「北京南→上海虹桥」和「北京→上海」现在都是「北京→上海」，图上少了一个区分：从北京站出发和从北京南站出发，对用户是不同的。车站级 provider 是临时的对照手段，长期需要"城市搜索 + 车站展示"两层结构。
5. **阶段 5 并发测绘仍未做**。现在的数据量（3 个 OD、1317 条边）离真实规模（城市数 316 的平方量级）差得远，吞吐和封禁阈值都还没有数据。
