# 流式搜索接口收敛实施计划

## 1. 背景

当前后端 API 同时暴露三类查询接口：

```text
GET  /api/stations/search
POST /api/routes/search
POST /api/routes/search/stream
```

其中：

- `/api/stations/search` 直接依赖 `TrainDataProvider` 上的非正式 `search_stations` 能力；
- `/api/routes/search` 是非流式路线搜索接口；
- `/api/routes/search/stream` 是当前前端实际使用的流式路线搜索接口。

这导致 API 层同时知道 `provider` 和 `route_search_engine`，边界不清晰。

当前代码中的核心问题：

```python
provider = create_train_data_provider()
route_search_engine = create_route_search_engine(provider)
```

随后：

```text
/stations/search       -> 直接调用 provider
/routes/search         -> 调用 route_search_engine.search()
/routes/search/stream  -> 调用 route_search_engine.stream_snapshots()
```

这种结构会削弱 `RouteSearchEngine` 抽象的意义，也会让 provider 和 engine 两个概念混在一起；历史上的 `RouteSearchService` 命名也会混淆搜索引擎实现与 service 层职责。

## 2. 目标

本轮目标是收敛对外路线搜索 API，只保留流式路线搜索入口。

最终保留：

```text
GET  /api/health
GET  /api/providers/status
POST /api/routes/search/stream
```

删除：

```text
GET  /api/stations/search
POST /api/routes/search
```

站点补全能力暂时移除，后续重新设计并接入。后续不应继续把站点搜索作为 `TrainDataProvider` 的隐式可选方法暴露给 API 层。

## 3. 概念边界

### 3.1 Provider

`TrainDataProvider` 是数据源适配器，当前正式抽象只包含：

```python
async def search_segments(...)
def candidate_transfer_stations(...)
```

它负责提供 OD 段数据和候选中转站，不负责完整路线搜索。

### 3.2 Engine

`RouteSearchEngine` 是路线搜索策略接口，当前包含：

```python
source
status
search(query)
stream_snapshots(query)
```

API 层应尽量只通过 engine 接触路线搜索能力。

### 3.3 ProviderBackedRouteSearchEngine

`ProviderBackedRouteSearchEngine` 是 candidate/legacy 搜索引擎实现。它基于 `TrainDataProvider` 查询 OD 段，然后组合直达、中转、多次中转方案，并负责缓存、限流、剪枝、排序和诊断。

命名使用 `ProviderBackedRouteSearchEngine`，避免继续用 `Service` 混淆实现类与 `RouteSearchEngine` 抽象的关系。

## 4. 实施范围

### 4.1 后端 API

文件：

```text
backend/app/api/routes.py
```

计划改动：

1. 删除 `GET /stations/search` 路由。
2. 删除 `POST /routes/search` 路由。
3. 保留 `POST /routes/search/stream`。
4. 保留 `GET /providers/status`。
5. 保留 `GET /health`。
6. 将变量命名从：

   ```python
   provider = create_train_data_provider()
   route_search_engine = create_route_search_engine(provider)
   ```

   调整为：

   ```python
   train_data_provider = create_train_data_provider()
   route_search_engine = create_route_search_engine(train_data_provider)
   ```

   这一步不改变行为，只减少概念混淆。

7. 如果删除路由后 `RouteSearchResponse`、`StationSearchResponse` 不再被 `routes.py` 使用，则同步删除 import。

### 4.2 前端 API 封装

文件：

```text
frontend/src/lib/api.ts
```

计划改动：

1. 删除 `searchStations()`。
2. 删除 `StationSearchResponse`。
3. 删除 `searchRoutes()` 非流式请求函数。
4. 保留 `searchRoutesStream()`。
5. 保留 `getProviderStatus()`。

### 4.3 前端页面逻辑

文件：

```text
frontend/src/App.tsx
```

计划改动：

1. 删除 `searchStations` import。
2. 删除起点输入框的站点补全请求逻辑。
3. 删除终点输入框的站点补全请求逻辑。
4. 删除站点建议列表相关状态和渲染。
5. 保留手动输入站名。
6. 路线查询继续只调用 `searchRoutesStream()`。

### 4.4 后端测试

文件：

```text
backend/tests/test_api.py
```

计划改动：

1. 删除 `/api/stations/search` 测试。
2. 删除 `/api/routes/search` 测试。
3. 将依赖非流式搜索触发诊断状态的测试改为调用 `/api/routes/search/stream`。
4. 保留流式接口测试。
5. 保留参数校验测试，但目标接口改为 `/api/routes/search/stream`。

## 5. 非目标

本轮不做以下事情：

1. 不重新实现站点补全。
2. 不把站点补全塞进 `RouteSearchEngine`。
3. 不改变 `RouteSearchEngine` 协议。
4. 不删除 `ProviderBackedRouteSearchEngine.search()` 方法，因为它仍可能作为 engine 内部能力或测试入口存在。
5. 不删除 provider 实现中的 `search_stations()` 方法；这些方法后续可在重新设计站点补全时评估是否保留、迁移或删除。

## 6. 后续站点补全设计方向

站点补全后续应单独设计，不应继续由 API 层通过 `getattr(provider, "search_stations", None)` 调用。

可选方向：

### 6.1 独立 StationSearchService

新增：

```text
backend/app/services/station_search.py
```

职责：

- 根据关键字返回站点列表；
- 可基于静态站点表、SQLite、本地缓存或远程站点源；
- 与路线搜索 engine 解耦。

### 6.2 前端本地站点索引

如果站点列表规模可控，可以将站点数据构建为前端静态资源，由前端本地搜索。

优点：

- 无需补全 API；
- 输入体验更快；
- 不依赖 provider。

缺点：

- 需要维护站点数据更新机制。

### 6.3 后端静态站点 API

重新提供类似接口，但不要挂在 provider 上：

```text
GET /api/stations/search
```

该接口可以恢复，但实现应依赖明确的 `StationSearchService`，而不是 provider 的隐式方法。

## 7. 验证标准

### 7.1 后端验证

执行：

```bash
cd backend
python -m pytest
```

预期：

- 后端测试通过；
- 不再存在针对 `/api/routes/search` 的测试；
- 不再存在针对 `/api/stations/search` 的测试；
- `/api/routes/search/stream` 测试通过。

### 7.2 前端验证

执行：

```bash
cd frontend
pnpm typecheck
```

如项目没有 `typecheck` script，则执行：

```bash
cd frontend
pnpm build
```

预期：

- TypeScript 编译通过；
- 不再引用 `searchStations()`；
- 不再引用 `searchRoutes()`；
- 路线查询仍使用 `searchRoutesStream()`。

### 7.3 手动验证

启动后端和前端后检查：

1. 页面可以手动输入起点、终点、日期并发起查询；
2. 查询结果通过流式接口逐步返回；
3. 站点输入框不再请求后端补全；
4. 访问旧接口应返回 404：

   ```text
   GET  /api/stations/search
   POST /api/routes/search
   ```

## 8. 风险

### 8.1 用户体验下降

删除站点补全后，用户必须手动输入准确站名。

处理方式：后续单独实现站点补全，不在本轮混入。

### 8.2 外部调用方兼容性

如果已有外部脚本调用 `/api/routes/search` 或 `/api/stations/search`，删除后会破坏兼容。

当前判断：项目处于开发阶段，可以接受直接删除。

### 8.3 测试需要同步调整

现有测试覆盖了旧接口，必须同步删除或改写，否则测试会失败。

## 9. 建议提交顺序

1. 修改后端 `routes.py`，删除旧路由并统一命名。
2. 修改前端 `api.ts`，删除旧请求函数和类型。
3. 修改 `App.tsx`，去掉站点补全调用和 UI。
4. 修改后端 API 测试。
5. 运行后端测试。
6. 运行前端类型检查或构建。
7. 手动验证流式查询。

## 10. 最终状态

完成后，路线搜索对外只有一个写接口：

```text
POST /api/routes/search/stream
```

API 层的路线搜索调用路径收敛为：

```text
routes.py
  -> route_search_engine.stream_snapshots(query)
      -> ProviderBackedRouteSearchEngine(candidate/legacy)
      -> TimeExpandedRouteSearchEngine(time-expanded)
```

站点补全从本轮范围中移除，后续作为独立能力重新设计。
