## 3. 主线一：远程 OD 查询成为瓶颈

搜索算法阶段结束后，第一段应该明确转折：

> 真正的瓶颈不是 Python 本地组合 `TransferPlan`，而是远程 OD 查询被中转搜索放大。

一次一换搜索的远程查询规模大致是：

```text
直达 A -> B
候选中转站 T1..Tn
每个 T 最多查询 A -> T 与 T -> B
```

如果候选站数是 50，就可能产生 100 次左右的 OD 查询。二换搜索还会进一步扩大搜索空间。即使有请求预算和并发限制，用户体验仍然受制于外部接口。

这一节要强调两个判断：

1. 请求预算、Semaphore、失败容错只能让系统“不失控”，不能让外部接口变快。
2. 后续收益更大的方向是缓存、持久化、遥测和静态票价库，而不是继续局部优化循环。

推荐小节标题：

```markdown
## 远程 I/O 比本地搜索更早成为瓶颈
```

## 4. 主线二：SQLite OD 持久化缓存

### 4.1 为什么内存 TTL 不够

早期内存 TTL 缓存解决的是短时间重复查询问题，但它有明显边界：

- 服务重启后缓存丢失。
- 多次运行之间不能复用。
- 无法分析哪些 OD 高频出现。
- 无法作为后续静态票价库和刷新队列的基础。

所以项目引入 SQLite OD 持久化缓存。缓存粒度继续保持与远程 provider 一致：

```text
provider + travel_date + origin + destination -> list[TrainSegment]
```

这个设计重要，因为它没有把缓存绑定到某个算法阶段，而是绑定到铁路票价接口的自然查询单位：某日某 OD 的车次段。

### 4.2 查询链路

写作时可以用这张链路图：

```text
RouteSearchService._search_segments()
  ↓
内存 TTL 缓存
  ↓ miss
SQLite OD 持久化缓存
  ↓ miss
TrainDataProvider.search_segments()
  ↓
远程 12306 公布票价接口或其他 provider
```

SQLite 命中后有两个效果：

- 回填内存缓存。
- 不增加 `remote_query_count`。

这让缓存不仅影响性能，也影响请求预算消耗。

### 4.3 Provider 错误处理

真实 provider 的失败不应该直接变成进程异常。需要区分：

- 站名无法映射。
- HTTP 请求失败。
- 接口返回非 JSON 或异常结构。
- 票价字段缺失或无法解析。
- 单个候选 OD 失败。

API 层应把这些失败转换成受控响应。这样用户看到的不是“系统炸了”，而是明确的数据源不可用、候选失败或预算耗尽。

推荐小节标题：

```markdown
## 从进程内缓存到 SQLite OD 缓存
```

## 5. 主线三：搜索诊断、流式输出和遥测

### 5.1 为什么需要诊断

路线搜索和普通 CRUD 不同，空结果不一定表示没有路线，也不一定表示系统错误。可能原因包括：

- 候选站没有覆盖到关键通道。
- 静态库没有覆盖对应 OD。
- 远程 provider 某个 OD 请求失败。
- 请求预算提前耗尽。
- 换乘时间或总耗时约束过滤了方案。
- 当前 provider 本身只覆盖少量样例数据。

因此前端只展示“无结果”是不够的。系统需要暴露搜索诊断。

### 5.2 流式接口

新增流式搜索接口：

```text
POST /api/routes/search/stream
```

返回 NDJSON，每一行是一个 `TransferPlan` 或错误事件。前端通过 `ReadableStream` 增量消费，避免等所有候选站都查询完成后才显示结果。

这适合真实 provider 场景：中转搜索可能慢，先返回已有方案比等待全量搜索完成更合理。

### 5.3 Provider 状态与诊断面板

诊断面板建议重点写这些字段：

- 当前 provider。
- 当前搜索引擎。
- 最大远程请求数。
- 并发上限。
- 最近一次远程请求数。
- 缓存命中情况。
- 候选站扩展情况。
- provider 错误。
- 是否在线远程 I/O。

### 5.4 SQLite 搜索遥测

`SqliteSearchTelemetryRecorder` 的意义不是“多记几行日志”，而是建立后续刷新闭环。

遥测记录：查询时间、provider、出发地、目的地、出行日期、最大中转次数、换乘约束、方案数量、最佳价格、最佳中转站和远程请求数。

`transfer_station_hits` 记录某 OD 下中转站的命中次数和历史最佳价格。

推荐写成闭环：

```text
用户搜索
  ↓
search_runs / transfer_station_hits
  ↓
export_refresh_od_from_telemetry.py
  ↓
data/refresh_od.csv
  ↓
refresh_static_prices.py
  ↓
data/static_prices.sqlite3
  ↓
后续搜索优先本地命中
```

推荐小节标题：

```markdown
## 让搜索过程变得可解释、可统计、可反哺
```

## 6. 主线四：SQLite 静态票价库

### 6.1 为什么不是继续调算法

到这里，项目做出了一个关键判断：

> 短期不应继续主要微调在线搜索循环，而应建立本地静态票价库，用稳定公布票价降低真实 provider I/O。

原因：公布票价相对稳定，用户搜索通常集中在热门 OD，候选中转 OD 可以从历史命中推导，本地 SQLite 查询比实时访问 12306 稳定，全国 OD 暴力枚举不可接受。

### 6.2 产品语义

这里必须写清楚边界：

```text
静态票价库提供：公布票价 / 历史观测票价快照
静态票价库不提供：实时余票、实时停运、购票可用性、动态折扣保证
```

这能避免把项目写成“实时全国最低价购票系统”。

### 6.3 第一版核心表

第一版 SQLite 静态票价库核心表：

| 表 | 作用 |
| --- | ---- |
| `station_snapshot` | 预留保存站名、电报码、拼音、抓取时间等站点快照 |
| `od_public_price_snapshot` | 保存某日某 OD 某车次某席别的公布票价 |
| `od_min_price_snapshot` | 保存 OD 最低价聚合结果 |
| `crawl_job` | 记录刷新任务 |
| `crawl_task` | 记录刷新任务中的单个 OD |

`od_public_price_snapshot` 是主表。它选择按席别拆行，价格用文本保存 Decimal，避免浮点误差。

### 6.4 Provider 模式

静态票价库接入后，Provider 工厂支持：

```text
TRAIN_DATA_PROVIDER=mock
TRAIN_DATA_PROVIDER=12306-public-price
TRAIN_DATA_PROVIDER=static-price
```

`static-price` 下有两种主要模式：

```text
static-only
  只读本地 SQLite，未命中即无结果

static-with-remote-fallback
  先读本地 SQLite
  未命中或过期时调用 12306 provider
  成功后写回 SQLite
```

这一节的重点不是 SQL，而是架构形态变化：

```text
实时请求器
  -> 本地静态数据优先
  -> 远程 provider 补洞
  -> 遥测反哺刷新
```

推荐小节标题：

```markdown
## 静态票价库：把远程响应变成可复用资产
```

## 7. 主线五：候选站 OD 试探的正确性边界

静态库和 fallback 缓解了远程 I/O，但没有彻底解决旧搜索模型的边界。

旧模型本质是：

```text
先猜候选站 T
再查 A -> T
再查 T -> B
```

只要关键通道节点没有进入候选集合，后续搜索就不会触发对应 OD 查询。即使 provider 能查到票价，也不会返回方案。

`东莞 -> 拉萨` 是典型案例：地理走廊容易把候选站集中在华南、西南，但真实可行路线可能需要 `郑州`、`西安`、`兰州`、`西宁` 等进藏通道节点。如果这些节点没有进入候选集合，搜索就会失败。

后续文档中应避免“低价站点”“低价断点”的说法。更准确的概念是：换乘枢纽先验、铁路通道先验、车型/线路切换先验、历史命中先验。

结论要写清楚：

> 候选站生成是受请求预算约束下的启发式召回，不是正确性证明。

推荐小节标题：

```markdown
## 候选站不是正确性保证
```

## 8. 主线六：RouteSearchEngine 与时间扩展图

### 8.1 为什么需要新搜索架构

`厦门 -> 深圳` 排查暴露了另一个问题：某些关键边本地缺失，fallback 理论上能补，但旧二换搜索会先消耗大量 OD 查询预算，关键边未必有机会被补查。

这说明问题不只是候选站召回，而是旧模型在线搜索时会无序消耗 fallback 预算。

因此项目转向：

```text
离线/准实时构建本地时间扩展图
在线执行 Dijkstra 或 label-setting 最短路搜索
```

### 8.2 不把新算法塞进旧服务

旧 `RouteSearchService` 已经承担候选中转站 OD 试探搜索、provider 调度、缓存、请求预算、并发控制、遥测和 fallback。如果把时间扩展图直接塞进去，会让旧搜索和新搜索互相耦合。

所以项目引入 `RouteSearchEngine` 抽象：

```text
API 层
  ↓
RouteSearchEngine
  ├─ candidate：旧候选站 OD 搜索
  └─ time-expanded：本地时间扩展图搜索
```

环境变量：

```text
ROUTE_SEARCH_ENGINE=candidate
ROUTE_SEARCH_ENGINE=time-expanded
```

### 8.3 time-expanded 的边界

`time-expanded` 在线搜索必须强调这些边界：

- 只读本地 SQLite。
- 不调用 `TrainDataProvider.search_segments()`。
- 不触发 12306 远程 fallback。
- 本地数据缺失时返回空或覆盖不足诊断。
- 不宣称全国完整覆盖。
- 不把静态公布票价等同于实时有票。

### 8.4 时间扩展图的基本模型

可以用简化描述，不必展开完整代码：

```text
车站时间事件 = 节点
乘车区间 = 带价格和时间的边
同站等待/换乘 = 时间可达边
搜索目标 = 在换乘、时间约束下寻找最低票价路径
```

快速落地版当前读取本地 SQLite 中的 `train_od_price_snapshot` 或基础边数据，将相对时刻按查询日期展开。

推荐小节标题：

```markdown
## 从候选站 OD 试探到本地时间扩展图
```

## 9. 主线七：全量快照与相邻区间票价验证

时间扩展图需要本地边。问题变成：边从哪里来。

### 9.1 快速全量快照

2026-07-01 后项目收敛为快速落地方案：

```text
不优先处理每日开行日历、实时余票、增量更新或在线 fallback
先基于一次全量时刻表和公布票价快照，让 time-expanded 能返回路线方案
```

基础边使用相对时刻：

```text
depart_time
arrive_time
depart_day_offset
arrive_day_offset
```

在线查询时再按用户查询日期展开。这个取舍要写清楚：快速可用，但暂不处理真实开行日历和临时停运。

### 9.2 时刻表优先落库

采集脚本先支持 `--train-info-only`：写入 `train_service_snapshot` 和 `train_stop_snapshot`，不生成价格任务，不调用 `queryAllPublicPrice`。这样可以先把时刻表采集和票价采集解耦。

### 9.3 相邻票价任务模式

同车全部 OD 是 `i < j` 规模，任务数增长很快。于是新增：

```text
--price-task-mode all
--price-task-mode adjacent
```

`adjacent` 只生成相邻区间 `i -> i+1`，用于降低第一阶段采集规模。

但必须强调：

> 相邻区间累加不等于同车长区间真实单票公布票价。

它只能作为图搜索近似边权或分段购票成本，是否可用必须由误差报告支撑。

### 9.4 station OD 去重请求

多个 train OD 可能共享同一个 station OD。脚本改为按 `(from_station, to_station)` 去重请求：

```text
多个 PriceTask
  ↓ group by station OD
一次 queryAllPublicPrice
  ↓ rows 分发
匹配不同 train_no / train_code
  ↓ 写入边
```

这一步减少远程请求数量，同时保持 train task 的写入语义。

### 9.5 direct-vs-adjacent 误差验证

新增 `compare_adjacent_vs_direct_price.py`，用于比较 direct OD 公布票价与相邻段累加票价。

输出包括样本数、完全一致数量、有误差数量、平均绝对误差、最大绝对误差和按席别统计。

这一节体现数据工程方法：可以先降低采集成本，但必须用误差报告约束语义，不能把近似数据写成真实长 OD 票价。

推荐小节标题：

```markdown
## 时间扩展图需要数据工程，而不只是算法
```

## 10. 主线八：云函数 worker 与 PostgreSQL 中心任务库

本地长跑脚本能验证思路，但采集规模扩大后会遇到单机运行时间长、中断恢复麻烦、失败任务需要重试、并发吞吐受限、缺少统一状态管理等问题。因此项目开始设计云函数 worker 化采集。

### 10.1 设计边界

必须强调：云 worker 不是直接替换在线搜索，也不是直接写本地静态库。

边界：

- worker 只处理 `unique station OD`。
- 先写原始响应摘要或对象存储。
- 不直接写 `train_od_fare_edge`。
- 最终由离线 merge 完成基础边写入。
- 真实接口 PoC 必须有门禁。

### 10.2 任务状态机

核心状态：

```text
pending
  -> leased
  -> succeeded
  -> retry_wait
  -> dead_letter
```

需要支持 lease 防止重复处理、retry/backoff、dead-letter、过期 lease 回收、dry-run 释放任务和 response 摘要幂等写入。

### 10.3 PostgreSQL repository

2026-07-03 后，中心任务库已经从内存 repository 推进到 PostgreSQL：

- `postgres_schema.sql` 定义中心任务库 schema。
- `PostgresCloudCrawlRepository` 使用 `FOR UPDATE SKIP LOCKED` 领取任务。
- 集成测试验证 claim、lease token、retry、dead-letter、response 幂等写入、lease 回收。
- 本地 `sampled_probe` 和 mock worker 已跑通 PostgreSQL-backed 闭环。

当前仍应写清限制：尚未运行真实 12306 PoC，worker 仍未接入在线搜索链路，不应把包含密码的 DSN 提交到 Git。

推荐小节标题：

```markdown
## 为什么采集不能只是一个 for 循环
```

## 13. 当前限制必须写清楚

博客必须客观写限制，避免把项目能力夸大：

- `candidate` 搜索仍是启发式候选站搜索，不保证全国全局最低价。
- `time-expanded` 只读本地 SQLite，数据覆盖不足时会返回空或不完整结果。
- 快速全量快照方案暂不处理真实开行日历，可能把导入车次视为每日可用。
- 相邻区间累加不是同车长区间真实单票公布票价，只能作为近似边权或分段购票成本。
- 静态票价库不代表实时余票、实时停运或可购票状态。
- 12306 公布票价接口不是公开稳定 API。
- 云函数 worker 已验证 mock/PostgreSQL 基础闭环，但仍未运行真实 12306 PoC。
- worker 不应直接接入在线搜索链路，也不应绕过离线 merge 写入基础边。

## 15. 可直接使用的开头草稿

```markdown
# HardSeat Hero：从候选站搜索到时间扩展图的最低价铁路路线搜索器

HardSeat Hero 最初只是一个最低价火车路线搜索 MVP：输入出发地、目的地和日期，返回直达或中转方案，并按总票价排序。

前期项目已经完成了 Mock provider、12306 公布票价 provider、候选中转站搜索、请求预算、并发控制、最低价剪枝、UCS 和 Pareto frontier。到这个阶段，搜索算法已经能受控运行。

但真正的瓶颈也随之暴露：中转搜索会把一次用户查询放大成大量 OD 查询。只要每条边都实时访问远程票价接口，系统就会受网络延迟、接口稳定性、请求预算和限流风险约束。

所以后续演进的重点不再是继续微调本地搜索循环，而是把远程查询沉淀为可缓存、可诊断、可刷新、可复用的数据资产。项目因此引入 SQLite OD 缓存、搜索遥测、静态票价库和 fallback；当候选站 OD 试探暴露正确性边界后，又进一步转向 RouteSearchEngine 多重搜索架构和本地时间扩展图；最后，数据采集也从本地长跑脚本逐步演进到相邻区间误差验证和云函数 worker 任务系统。
```

## 16. 可直接使用的结尾草稿

```markdown
HardSeat Hero 当前仍不是生产级火车票系统。它不承诺实时余票，不处理购票，不处理登录，也不宣称全国全局最低价。

但这个项目已经验证了一条更稳妥的演进路线：先用 Provider 抽象隔离真实数据源，再用受控搜索避免远程请求失控；随后通过 SQLite OD 缓存、搜索遥测和静态票价库把远程响应沉淀为本地数据资产；当候选站 OD 试探暴露正确性边界后，再引入 RouteSearchEngine 和时间扩展图，把在线搜索从“边搜边查”转向“本地图上求解”。

后续真正困难的部分不只是算法，而是数据覆盖和采集工程：哪些 OD 值得刷新，如何验证相邻区间票价误差，如何控制真实接口请求，如何用中心任务库管理 worker 的 claim、lease、retry 和 dead-letter。只有这些边界都清楚，最低价铁路路线搜索才不会停留在一次性的接口脚本。
```
